# Voice answering is not background-only; transcript and grade stream over one Firebase Callable connection

## Decision

**1. Voice answering is not a background-only feature.** Screen-on (user watching the study session, reading their recognized answer and then the grade in the bottom sheet) and screen-off/pocket (hands-free, audio-only feedback) are **equally first-class** use cases. Every prior document/ADR framing this feature as fundamentally a "background, phone-in-pocket" capability — with screen-on treated as an incidental side case — is superseded. This does not touch ADR-0027's BT/screen-off mechanics (those remain correct for the screen-off case); it only corrects the framing that screen-off was ever the *primary* or *sole* case.

**2. The grading pipeline's client↔server call becomes a single Firebase **streaming callable function**, not the current plain HTTPS proxy (ADR-0024).** One client request delivers two results over one connection, in order:
   1. `{sanitizedTranscript}` — as soon as STT + sanitize finish.
   2. `{grade, feedback}` — the function's final return value, once the grading LLM call finishes.

   No second request from the client triggers phase 2 — the server keeps the same connection open and the client keeps collecting from the same `Flow`.

**3. The transcript displayed to the user (in the bottom sheet, from its arrival until the grade replaces it, for at least one second — [ADR-0053](0053-voice-answer-sheet-states-and-live-input-level.md)) is the *sanitized* transcript** (PII-stripped, filler/disfluency-normalized — "um", "uh", repeated words removed), not the raw ElevenLabs Scribe output. This means sanitize must run as part of phase 1 (transcribe stage), not bundled solely into phase 2 (grade stage) as the current single-combined-LLM-call design has it.

**4. Mechanism: Firebase's native streaming callable functions**, not a hand-rolled raw-HTTP streaming proxy. Verified against live Firebase documentation (see Verification below):
   - **Client (Kotlin):** `functions.getHttpsCallable("gradeVoiceAnswer").stream(requestData).asFlow().collect { response -> when (response) { is StreamResponse.Message -> /* sanitized transcript chunk */; is StreamResponse.Result -> /* final {grade, feedback} */ } }`
   - **Server (Node, 2nd gen, TypeScript):** must use `onCall()` (the `functions.https` callable API — *not* `onRequest`/Express, which is what ADR-0024's current proxy uses). Inside the handler: check `request.acceptsStreaming`, call `response.sendChunk({ sanitizedTranscript })` once phase 1 finishes, then `return { grade, feedback }` as the normal function result — Firebase delivers that as the final `StreamResponse.Result` over the same connection.
   - Minimum versions: Android Firebase SDK **22.1.1+**, Web SDK v9.7.0+, requires Cloud Functions **2nd gen**.
   - Backward compatible: a non-streaming caller (`request.acceptsStreaming == false`) gets chunks silently buffered and the full response sent once — so the existing debug-screen single-call test blocks keep working unmodified.

## Context

This surfaced while investigating a state-machine bug: tapping "skip to answer" while voice-answering was actively listening for a spoken response left the mic hot while the TTS spoke the answer aloud, so the app graded its own voice. Fixing that (done — see Consequences) led to a broader question about whether Rated-mode navigation should let users freely revisit already-answered cards. The answer (freely navigate, but **read-only** for already-answered cards, both manual-rating and voice-answering variants) requires being able to show the user's own answer alongside the question when revisiting — which for voice-answering means the *transcript* of what they said, not just the grade. That in turn surfaced that the current pipeline (ADR-0024) has no mechanism to get a transcript back to the client at all before the full grade is ready, and the existing design doc explicitly assumed no visible transcript would ever be needed ("this feature deliberately runs in the background with no visible transcript" — `premium-voice-grading-pipeline.md`, "Proxy shape" section, now incorrect).

The read-only-revisit and Attempt/Terminal-State tracking work itself is **not** designed or built by this ADR — that remains future work (see ADR-0026's reference to the not-yet-written Rating/Attempt/Terminal-State pipeline). This ADR only guarantees the transcript will exist and reach the client promptly enough to display grading feedback during the session (see Consequences — no transcript is persisted), and fixes the pipeline's shape and the background-only framing now rather than having them designed to disagree later.

## Verification performed before writing this ADR

Because this is a real architectural pivot away from ADR-0024's plain-HTTPS-proxy shape, the feasibility was checked directly rather than assumed:

1. **Transport-level proof.** A local Node PoC (throwaway, not part of the codebase) mimicked exactly what a `res.write()`-then-delayed-`res.write()`-then-`res.end()` handler does — the same primitive Cloud Functions' Node runtime uses under the hood. A client reading the response incrementally received chunk 1 at **+33ms** and chunk 2 at **+1536ms** (matching a deliberate 1500ms server-side delay) — proving genuine incremental delivery over one HTTP connection, not response buffering.
2. **Vendor API verification.** Fetched Firebase's live documentation (not recalled from training data) for both the Android/Kotlin client API (`getHttpsCallable(...).stream(data).asFlow()`, `StreamResponse.Message`/`StreamResponse.Result`, `kotlinx-coroutines-reactive` dependency, min SDK 22.1.1) and the Node server API (`onCall`, `request.acceptsStreaming`, `response.sendChunk()`, must-be-`onCall`-not-`onRequest` constraint). Both confirmed current and generally available, not preview/experimental.
3. **Dependency check.** This project currently has no `firebase-functions` dependency at all (only `firebase-auth`, `firebase-firestore` — see `gradle/libs.versions.toml`); the Cloud Function proxy today is called via Retrofit/OkHttp as a plain REST endpoint. Adding `firebase-functions` (KTX merged into the base artifact, consistent with this project's existing `firebase-auth`/`firebase-firestore` alias convention — no `-ktx` suffix) is a net-new but small addition.

## Alternatives considered


**Raw OkHttp streaming (manual NDJSON over a plain HTTP endpoint).** This was the original plan and the local PoC above was built to validate it. Rejected once the Firebase-native mechanism was confirmed available: it would reinvent auth-token attachment, error framing, and chunk parsing that the Firebase SDK already provides, for no benefit — this project is already Firebase-centric (Auth, Firestore) and gets automatic ID-token verification (`request.auth`) for free with `onCall`, which a raw endpoint would still need `FirebaseAuthTokenInterceptor` for.

**Push the grade back via a Firestore realtime listener** (server writes result document, client already-listening picks it up), keeping phase 1 as a normal single-response HTTP call. Rejected: this means a per-card Firestore write *during* the session, directly contradicting ADR-0014 ("no writes during a session, batch write at Summary screen only," rejected there specifically for write-volume reasons at session scale — the same volume concern applies here regardless of which side initiates the write).

**Two literal separate round-trip HTTP calls** (client calls transcribe endpoint, waits, then explicitly calls a second grade endpoint with the transcript). This is what the existing debug-only `transcribe()`/`sanitizeAndGrade()` split on `VoiceGradingApi` already models, and it does work — but the user explicitly asked to avoid the latency of a second connection setup/auth round-trip for the *production* path. Streaming one connection avoids that while still giving the caller two discrete, ordered results.

**Bundle sanitize into the grade LLM call only** (current design), showing the *raw* ElevenLabs transcript immediately in phase 1 instead. Rejected per decision 3 above — filler words and disfluencies in a raw ASR transcript read poorly on screen and would need re-doing once sanitize eventually runs anyway; moving sanitize into phase 1 costs one LLM call's worth of latency (unavoidable either way) but avoids ever showing throwaway text to the user.

## Consequences

- **Already implemented as part of this same work session:** manual "skip to answer" / previous / next controls in the Rated voice-answering bottom sheet are disabled while `VoiceAnswerState.phase` is `LISTENING`, `SPEECH_DETECTED`, `GRADING` or `SPEAKING_NOTICE` (`RatedVoiceTransportRow`); during a voice round the sheet shows no transport row at all ([ADR-0053](0053-voice-answer-sheet-states-and-live-input-level.md)) — this was the proximate bug (skip-to-answer mid-question left the mic listening while TTS read the answer, grading its own voice) and is fixed independently of the pipeline rework above.
- `docs/design/premium-voice-grading-pipeline.md` needs updating (companion edit alongside this ADR) to: drop the "background-only" framing throughout, replace the "Sanitize + grade: one combined LLM call" section and end-to-end pipeline diagram with the two-phase streamed shape, and note the `onCall`/streaming-callable proxy shape supersedes ADR-0024's `onRequest` proxy for this one endpoint.
- **Not designed by this ADR, left as explicit follow-up work:**
  - The read-only-revisit UI for already-answered cards (both manual-rating and voice-answering Rated variants). The pipeline itself is now designed — ADR-0044 (Terminal State), ADR-0046 (re-insertion), ADR-0016 (card progress), ADR-0014 (session commit). No transcript is persisted anywhere — a voice-answered card's sanitized transcript is shown in the bottom sheet only while its grade is pending, then discarded; the session document's embedded `cardResults` map carries only the resulting `FlashcardResult.Rated` (Terminal State, Attempts used, previously-mastered flag) — voice grading only exists in Rated sessions. A revisit UI, if ever built, needs its own design and its own decision about persisting transcripts. This ADR does not build session-state tracking, navigation locking, or the revisit UI itself.
  - `VoiceGradingApi`/`VoiceAnswerGradingRepository`/`GradeSpokenAnswerUseCase` (currently `core/data`, `core/domain`) need to change shape from a single `suspend fun -> Result<VoiceAnswerGrade>` to something that surfaces two ordered events (e.g. a `Flow`/sealed-event return) — not implemented by this ADR.
  - `VoiceAnswerController` (`feature/study/.../voice/VoiceAnswerController.kt`) and `VoiceAnswerState` need a new field for the in-flight sanitized transcript (settable as soon as phase 1 arrives, ahead of `lastGrade`) — not implemented by this ADR.
  - `FakeVoiceGradingApi` needs to emit the same two-event shape (per this project's "fake it, don't stub" rule for blocked external dependencies) so the debug screen and the rest of the app can be exercised without a real deployment.
  - Migrating the WAV upload from Retrofit multipart to a callable function's JSON `data` payload means base64-encoding the audio (~320KB raw → ~426KB base64 for a typical utterance — negligible at this size, but a real payload-shape change from today's multipart request, worth a dedicated look at whether `checkEntitlement()` and other `VoiceGradingApi` members migrate to callable functions too or stay REST — left open).
  - No real ElevenLabs key, grading LLM key, or deployed Cloud Function exists yet (unchanged from ADR-0024's blocked-dependencies state) — the fake must model the two-phase shape realistically per the design doc's existing "Implementation strategy for blocked/inaccessible dependencies" rule.
